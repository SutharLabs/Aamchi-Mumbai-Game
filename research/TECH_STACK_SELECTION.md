# Technical stack selection - Mumbai: Gully Heat

Selected 20 November 2026 after checking current official engine documentation, the release archive and upstream sources. This is a **researched implementation choice**, not a claim that the engine is installed, a component is integrated or either exported build has passed. The user deferred Git/recovery/repeatable-export setup; no repository was initialized, SDK installed or prototype built for this decision. The [project record](../docs/PROJECT_RECORD.md), [roadmap](../docs/ROADMAP.md) and [phase tracker](../docs/PHASE_PROGRESS.md) own requirements, schedule and completed gates.

## Selected foundation

Use **Godot 4.7.2 stable, standard edition, typed GDScript, the Compatibility renderer on both Windows and Android, and built-in Jolt 3D physics**. Start with engine facilities and narrowly selected official examples. **No third-party runtime addon is required for the initial foundation.** Keep the advanced vehicle controller as a bounded optional comparison, not an architectural dependency.

This fits the small stylized district, common desktop/mobile code path and ten human hours/week better than inheriting a broad open-world framework. That is a project judgment, not a benchmark or a claim that Godot is universally faster than another engine. The release remains Windows and Android together; selecting a common baseline does not defer touch input, either export or the four required player-drivable families.

## OS compatibility is not the performance specification

Windows 10 and Android 12 are settled OS targets. The user's 8 GB/integrated-GPU Windows class is also settled as a class; exact CPU/GPU, memory arrangement, driver and test access are not established. Official simple-project requirements describe OpenGL 3.3 support for Compatibility on desktop, OpenGL ES 3.0 on mobile, and SSE4.2 for the x86_64 Windows CPU path. Godot explicitly says a game's actual CPU/GPU/RAM needs depend on its content and recommends low-end-device testing. Its simple-project examples are not a Mumbai open-world performance guarantee. [Official requirements](https://docs.godotengine.org/en/stable/about/system_requirements.html)

Android 12 specifies neither SoC nor RAM, GPU, driver quality, sustained thermal behavior or available memory. No physical Android minimum is selected by this research and no new phone question is needed to make the stack decision. Record a named test handset later, then accept the measured workload on it. Begin with the roadmap's provisional resolution/frame-time/population experiments, add scalable render resolution, and measure a sustained populated route on both native builds. Count driver/rider rigs, vehicle physics and touch UI as part of that workload. Do not treat remote Blender export timing or an editor FPS counter as the player-device result.

## OpenCity decision

**Do not use OpenCity as the project's base fork.** Retain it as an optional source reference for an individual, reviewed feature. This decision follows concrete mismatch costs, rather than a judgment that the project is unusable:

- Its configuration selects Godot 4.7/Forward Plus and MSAA, whereas this project selects Compatibility on both platforms. [Configuration](https://raw.githubusercontent.com/webgl-games/opencity/main/project.godot)
- Its traffic source explicitly uses right-hand lanes, rectangular grid constants and a fixed car count; it does not supply the selected irregular left-hand Bandra road graph. [Traffic source](https://raw.githubusercontent.com/webgl-games/opencity/main/scripts/traffic.gd)
- Vehicle switching binds a key directly and uses a fixed exit offset. Touch actions, clearance/ground checks, rider mounting and blocked-exit recovery require different integration. [Switching source](https://raw.githubusercontent.com/webgl-games/opencity/main/scripts/game.gd)

The [earlier repository audit](REPOSITORY_AUDIT.md) records MIT code and separate bundled-asset questions. None of those inspected pieces has been copied or tested here. Retaining only useful patterns avoids inheriting traffic geography, rendering, population and persistence assumptions that would need replacement. No OpenCity performance result is inferred.

When that work resumes, use these checks in order:

1. Acquire the exact standard editor/templates, record original URLs and hashes, preserve notices and verify the editor identifies itself as 4.7.2. Keep a deliberate upgrade record rather than tracking latest automatically.
2. Configure native Windows x86_64 and Android exports with the shared Compatibility renderer/GDScript code. Those are **future setup inputs**, not tools installed by this task. [Official setup](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)
3. Validate a minimal CharacterBody3D/camera/input/GLB scene on both OS/device paths before copying optional code. Inspect any demo source compatibility and constituent notices first. A successful import is not a frame-time result.
4. Compare the small built-in car baseline at the explicit starting tick rate. Only if it fails the concrete handling gate, run the bounded GEVP comparison and record its recommended tick-rate cost. Do not introduce a higher-frequency controller into the foundation by default.
5. Prove rickshaw and both motorcycle/scooter drivers/riders, touch and desktop controls, entry/mount, curb/slope/collision, blocked exit, recovery and saves. The required roster does not shrink when one controller fails; revise implementation and schedule using evidence.
6. Capture the same populated route on both native builds, with platform presets, frame-time/memory and sustained Android behavior recorded. Name tested physical hardware in the receipt. Accept actual minimums and component choices from those results; do not equate OS support with performance.

These choices settle the implementation direction while keeping acquisition, execution, gameplay and hardware acceptance honest.
