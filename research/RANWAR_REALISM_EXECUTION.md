# Ranwar realism execution brief

The next art and gameplay milestone is an approximately **200 m playable review route** through the existing Ranwar map. Start at St Peter’s BEST stop on Hill Road, pass the first row of shops and their public entrance, and include the approach to Nagrana Lane. Set the end marker using the measured path in Unreal. Record the actual in-game distance and any authored setback. Keep the larger Ranwar loop and its original mission playable.

The existing exchange places the BEST arrival and the Hill Road mouth of Nagrana Lane **162.44 m apart along the projected Hill Road centerline**. Continue about 38 m down the modeled pedestrian lane when a full 200 m route is needed. This is a game-map measurement calculated by projecting both anchors to the same polyline.

The current Unreal 5.8 project already has a mapped street level, Omkar’s skinned rig, four vehicle families, an authored arrival, traffic, two walk-in shops and paid deliveries. The Windows development build has run on the 16 GB Iris Xe development PC. The exact 8 GB Windows 10 minimum and the native Unreal Android package still require device tests. The earlier Godot APK run is recorded separately. [Current Unreal build](../unreal/README.md) · [Phase evidence](../docs/PHASE_PROGRESS.md) · [World and geography](../prototype/world/README.md)

## Copy-ready Codex prompt

```text
Work in C:\Suresh\Software\Aamchi-Mumbai-Game and follow this repository’s AGENTS.md. Build the next playable realism milestone for Aamchi Mumbai Game in the existing Unreal Engine 5.8 project.

Goal
Deliver an approximately 200 m stretch of contemporary Ranwar that looks and behaves like a lived-in part of Bandra West during normal play on modest hardware. Preserve the current story, gameplay, art ownership and scale. Use the first work order below as the implementation scope. Treat later orders as planning and measurement context until the first is reviewed.

Establish a baseline
1. Read unreal/README.md, unreal/ContentSource/RANWAR_STREET.md, docs/BUILD_WORKFLOW.md, docs/PHASE_PROGRESS.md, docs/RANWAR_REFERENCE_CHECKLIST.md and docs/THIRD_PARTY.md. Check Git status and identify the working native level, generator, character rig, traffic code and mission state before editing.
2. Use the pinned Unreal version and the standard Development command. Obtain baseline images from the running game at the BEST stop, public shop entrance, Nagrana approach and street-level driving view. Include the normal HUD, camera height, exposure, low preset, resolution and build identity. Record runtime failures separately from visual findings.
3. Measure approximately 200 m along the existing Hill Road playable pedestrian route from St Peter’s BEST arrival. Anchor the review to the arrival stop, occupied shop threshold and Nagrana approach. Identify any route endpoint adjustment needed to fit the actual mesh. Record metres, landmarks and site changes. Preserve the existing traffic lane, sidewalk connectivity, source road relationships and both shop entrances.
4. Record present-day visual references with their capture date and permitted use, the saved OSM way or parcel ID when applicable, station along the route, and what is documented versus authored. Use the existing map extract with its attribution. Use original photography, authorized source images, approved open textures or generated project-owned art for any source material that enters the asset pipeline. Keep model-source rights, attribution and adaptation notes with the exact source files. Use original names, surfaces, artwork, scenes and dialogue for the game.
5. Assign agents independent work with clear files. One prepares the route and references and owns geometry anchors. One makes a bounded frontage and street-material pass. One reproduces the baseline package and owns verification. Keep one integration owner for native project settings, map generation, publish and acceptance. Use the approved shared-node job pattern for CPU-heavy Blender work and collect receipts.

First work order. Make one street read as Mumbai at normal gameplay distance
- Retain current paths, parcel offsets, curb traversal, branded-game identity and stable spawn. Keep the route and surroundings playable throughout.
- Refine three existing anchors. Build a practical bus shelter/stop area with a clean walking line and sign, one Hill Road shop with a believable threshold and visible depth, and the Nagrana mouth with a narrow, shaded pedestrian-scale transition. Use present-day local reference to choose visible details. Where a parcel’s exact frontage is unverified, use original typology and record that choice.
- Give the anchors locally appropriate scale and surface response. Set window and shutter depth, sill and handrail heights, plinth/step heights, door widths, drain placement, road patchwork and the difference between paved, dusty and worn surfaces. Keep large-scale silhouettes readable at 720p. Use restrained close details such as painted fascia, queue rails, a small sign, shaded plaster, pipes and rainwater streaking. Preserve the driver’s view and actor clearance.
- Reuse the current Blender exchange and Unreal import workflow. Keep source and generated Unreal assets in their documented locations. Build a small shared palette with material instances and tightly sized textures. Prefer opaque surfaces and meshes with simple collision. Use repeatable seeds or editor-baked placement for noncritical clutter only if that reduces work. Use existing authored placement for landmarks, thresholds, mission actors and road rules.
- Keep a lightweight baseline for DX11/SM5 on Windows and use Unreal’s supported mobile rendering features for the phone profile. Test higher-cost lighting and effects only after profiling. Compare matched gameplay frames instead of judging beauty renders.

Later work orders for follow-through
A. Movement and camera. Improve Omkar’s existing locomotion with starts, stops, speed-matched feet, turns, curb transitions and more natural camera collision. Track foot slip, height and facing during a normal capture. Prototype animation retargeting with a small recorded set and confirm rig, clip and commercial project use before adoption. Compare simple blending against a narrow Motion Matching trial on the same device. Retain the current rig and verified controls unless the comparison justifies a change.
B. Street life. Reuse the existing traffic routes and interaction code. Add small varied NPC schedules, purposeful routes and sensible yields. Keep left-hand traffic, right-hand driving seats and sensible turning space. Test blocked road, pedestrian crossing, spawn/despawn inside and outside the camera, all four vehicle families, mission handoffs and save/load. Give expensive behaviors a near-player budget and retain lightweight distant decoration as needed.
C. Environment and sound. Add distinct, quiet ambient layers for Hill Road and Nagrana, purposeful footstep surfaces, vehicle feedback and restrained signage. Test clarity from a walking camera and a driver’s seat at default volume. Keep changes to rain, day/night and interiors individually measurable.
D. Streaming. Keep the first route resident while establishing a measurable baseline. If larger map scope raises memory or loading cost, prototype a small streamed district with HLODs. Keep collision, route/signal references and persistent mission state available at transitions. Drive over a cell seam at the fastest supported vehicle speed, walk back across it, teleport/recover, revisit and reload. Check visible pop, collision gaps, traffic queues, actor counts, save persistence and cold versus warm stalls.
E. Missions, economy and fiction. Grow the authored parcel-and-dabba loop into short original episodes. Define entry, handoff, alternate outcome, interruption, retry, rewards and save state for each mission. Add a small amount of optional work and persistent consequences. Prototype a fictional police attention loop using game events, feedback and disengagement rules. Treat character conflict and impacts as game mechanics. Validate each state transition and recovery with the earlier game-systems research.
F. Driving and traversal. Compare one compact hatchback and one two-wheeler against the existing handling on the same bend, curb and grade. Tune steering, brake distance, seat and mounting alignment, obstruction checks, cameras and the transition between idle and loaded audio. Add rickshaw and scooter cases before increasing traffic. Add playable BEST buses, rail or coastline mechanics separately with measured paths and platform budgets.
G. Interface and persistence. Keep status readable during driving and missions. Validate load, pause, input, low-graphics settings, volume, accessibility and recovery at 720p and on the target phone. Keep distinct stable identifiers for saves, vehicles, route anchors and mission states. Test missing or old saves, interrupted play and platform suspend/resume.


Performance and acceptance
- Windows target is a named Windows 10 integrated-GPU PC with 8 GB of system memory. Start at 1280×720 Low and a 30 FPS target. Use an uncapped warm capture to assess p95 frame time ≤33.3 ms, record the worst stalls and investigate recurring frames over 100 ms. Use the roadmap’s initial ≤2 GB process working-set guardrail and also measure system commit and shared GPU memory. These are starting budgets, not current measurements.
- Android target is Android 12 on the Redmi Note 9 Pro Max (India) when it is available. Record installed OS/MIUI, actual RAM, model/SoC/GPU, runtime renderer and resolution. Start at 30 FPS Low with scalable internal resolution. Capture native touch, interruption/resume, PSS or comparable memory, frame pacing, battery/thermal state and sustained behavior during a repeated 15-minute route. Measure under the phone’s own budget. A Windows or Godot pass does not certify the native Unreal Android build.
- Measure the same route, camera path, build revision, seed, active actor counts, resolution and quality at every comparison. Capture a cold entry, three warm traversals and a busy stop or junction. Use Stat Unit and Unreal Insights. Report game thread, render thread and GPU time where supported, p50/p95 frame time, stalls and memory. Log build size and full/incremental cook time when changing asset or build policy.
- Treat 8 nearby vehicles and 12 pedestrians as the roadmap’s experiment, not a requirement to raise the current limits. Start from actual current population. Benchmark one change at a time. If a change exceeds the target, reduce extra materials, transparent effects, visible prop variety or distant AI before shrinking the playable route.
- Run `powershell -NoProfile -File .\unreal\Tools\make-dev.ps1 -SmokeTest` to stage the Windows Development package. Add -RefreshMap for imported asset or generated map changes. Use the same EXE path and include its BuildReceipt.json. Walk the review route at normal speed and drive the connected road segment. Keep the Nagrana footway pedestrian-only. Repeat a shop entry/exit, an arrival conversation and an existing paid job. The smoke test and the rendered walk are separate evidence.
- Capture matched before/after frames and one normal-speed walkthrough. Include a short checklist with a pass, failure or pending-device result for each gate. Keep build logs, profiling data and screenshots outside the stable package. Keep source changes small, update the relevant existing project documentation, and stop expansion at the first failed acceptance gate while resolving the defect.
```
